# Harness 版本、ID 与状态规范

## 版本号

- 需求周期目录使用 `v<主版本>.<次版本>`，可选补丁版本，例如 `v1.2`、`v1.2.0`。
- 正则为 `^v\d+\.\d+(?:\.\d+)?$`。
- 周期目录标识支持 `<版本号>` 或 `<产品线>-<版本号>`；产品线允许中文、英文字母、数字、下划线与连字符，首字符不得为下划线或连字符。Manifest 的 `version` 与 `<版本号>-prd.md` 前缀必须等于解析出的产品版本（如 `v1.2`），不得把产品线前缀写入版本字段。
- 产品线周期的默认历史来源限定为 `history/<产品线>/`；跨产品线复用仅允许按 `project-assets.md` 显式登记并核验摘要的精确来源，其余引用必须失败。纯版本周期保留旧历史结构；混合布局时排除已由同级周期声明的产品线历史分区。
- 目录隔离不提供服务分支隔离；服务分支的 `develop-<版本号>` 仍基于产品版本。共享服务分支及历史版本别名必须依据真实执行记录处理，不自动改写。
- 未按 `project-assets.md` 登记的原型等非周期目录、缺失 Manifest、Manifest 版本不符继续报错；登记原型不属于需求周期，不能用来跳过任何真实周期的 角色 Gate。

## 稳定 ID

| 对象 | 格式 | 使用条件 |
| --- | --- | --- |
| 探索假设 | `HYP-<三位序号>` | Discovery 中待通过产品 Mock 验证的页面想法 |
| 产品决策 | `DEC-<三位序号>` | PRD 中需要跨阶段追溯的正式产品取舍 |
| 后端业务待确认 | `DEC-<三位序号>` | Plan 中影响查询范围/排序、状态流转、角色待办、计算口径、时间边界或缺省行为的业务缺口；需产品/业务 Owner 确认 |
| 后端技术待确认 | `TDEC-<三位序号>` | Plan 中涉及权限设计、数据库/DDL、Nacos、对象存储、消息、外部系统、容量或发布资源的实现取舍或前置条件；需架构/DBA/运维/权限 Owner 确认 |
| 本期功能分组 | `F-<三位序号>` | 仅用于 PRD「本期边界」功能分组，不参与跨阶段追溯 |
| 正式需求 | `REQ-<三位序号>` | PRD 中可独立验收的需求；跨阶段追溯以 REQ 为准 |
| PRD 修订 | `CHG-<三位序号>` | 该版本 PRD 首次生成后的每一次正文改动 |
| 研发任务 | `TASK-FE/BE-<三位序号>` | 前端或后端可独立实现与验证的任务 |
| 接口契约 | `CONTRACT-<三位序号>` | 需要跨服务或跨端追溯的接口文档 |
| 接口测试 | `IT-<三位序号>` | 后端本地接口测试用例 |
| TestHub 用例 | `CASE-<模块>-<三位序号>` | 同步到 TestHub 的 Markdown 用例 |
| 缺陷 | `BUG-<三位序号>` | Bugfix 流程中的可复现问题 |

ID 在同一版本内唯一，创建后不得因标题、排序、状态或文件移动而重编号。`HYP-*` 是探索假设，不代表产品已作出决定。`F-*` 不是 Gate 或追溯链节点。`CHG-*` 不拥有产品事实，记录开始追踪后的 PRD 操作及 Mock 日志中的独立改动，使用路径和编号区分各记录域。

PRD 的首次追踪和后续 CHG 记录见[产品修订规则](product-semantics-and-traceability.md#prd-修订)。

## 后端 Plan 待确认事项

- 新建或更新的 Plan 必须在既有“待确认事项”章节内分设“业务待确认事项”和“技术待确认事项”。
- 业务项使用 `DEC-*`，技术项使用 `TDEC-*`，由各自 Owner 确认。

## Manifest 阶段与运行状态

phase 保留 discovery、defining、planning、development、testing、completed，仅记录实际工作，不从 Gate 推导，不作为其他角色前置。
state 保留 active、blocked、cancelled，取消后不得新增交付。
四角色确认状态及其与 Manifest 的关系见 [Gate 规则](review-gates.md)。
