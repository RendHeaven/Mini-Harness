# 项目接入与执行约定

项目 Harness 使用 Atlas 时读取本规则；项目结构与专项约束由项目 AGENTS 和上下文索引持有。

## 开始工作

1. 以打开的项目 Harness 为项目根，读取其唯一配置（`harness/harness.yaml` 或 `.harness/harness.yaml`）。`core.localPath` 相对项目根解析；核对实际 Core 的版本、Git HEAD、内容锁与项目 pin，不自动改锁或切换 Core。
2. 读取项目结构表中的项目上下文、专项约束（如有）及配置指定的 `project.serviceCatalog`。周期根、历史根和阶段目录使用项目配置，不把模板路径或示例当成项目事实。
3. 在多仓工作区，先读取实际工作区根的 AGENTS.md，按其入口核对 meta 注册关系与共享消费者；项目服务目录中的声明不自动构成正式 binding。隔离 Core worktree 的目录深度可能不同，不从 Core 的固定相对层级推算工作区；由任务入口或已核实的项目位置定位并记录实际路径。
4. 读取实际周期的 Manifest、Execution 与所需阶段产物。项目必须采用当前 Schema 20 和 `.harness/` 配置目录；业务确认以实际负责人记录为准。

## 角色执行

- 沿用用户明确选择或会话已确定的角色；只有用户明确选择其他角色或流程后才切换。已安排的多角色顺序不重复确认。
- 职责模糊或请求超出当前边界时，询问用户本次按哪个角色处理；只暂停争议部分及依赖答复的工作，已明确且无依赖的当前角色工作可继续。
- 同角色阶段推进和返工正常执行；“回流”“交接”不授权跨角色代行。角色选择与交付确认的区别见 [Gate 规则](review-gates.md#角色执行约定)。

## 原型写入边界

产品和 UI 的代码修改仅限[项目共用原型](project-assets.md#项目原型与历史路径)，不修改真实前后端或共享组件库。各自文档写入配置指定周期的产品或 UI 目录。

## 跨仓操作

- 项目 Harness 保存产品事实、需求周期和交付证据；服务仓库保存源码、长期契约、构建、数据与运行事实，通过服务 ID、路径、revision 和必要摘要关联。
- 服务 `localPath` 相对项目 Harness 根解析。修改前读取目标仓库实际存在的 AGENTS.md；没有时读取 README、登记的上下文和相关工程配置。分别核对服务分支、HEAD 与已有修改，不自动 stash、reset、清理或切换分支。
- Harness 的独立 worktree 不包含同级服务；跨仓工作必须验证 Core 与服务实际路径。未登记的关系不凭目录或名称推定，历史和冻结证据保持原文。
- 修改配置、Hook 或工具时保留项目定制；跨范围改动遵循已有授权和目标规则。真实凭据仅保存在被忽略的本地配置，不进入模板、文档、命令参数或日志。

## 项目工具

- Jenkins：读取项目上下文的 `jenkins.md`、项目工具接入说明和 [Jenkins skill](../skills/delivery/jenkins.md)。按已有授权执行，不由 Review、Gate 或 Hook 自动触发构建。
- TestHub：读取项目配置与测试上下文，按 TestHub workflow 执行；模板文件存在不代表远端连接或运行授权。
- 数据库与其他项目工具：使用项目 `tools/README.md` 指定的入口和限制，不用通用模板替换既有实现。Hook 只承担已配置的采集职责，不代替阶段验证或 Gate。
