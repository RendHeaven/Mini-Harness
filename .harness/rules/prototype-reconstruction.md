# 页面还原协议

## 来源与真实性

- 最小单元是页面或区域与状态。以当前入口引用链确定可达性；文件存在不代表功能仍在使用，动态路由需结合菜单和运行证据。
- `observed`：在固定运行版本、角色、视口、数据条件下实际观察；`source-inferred`：从固定源码推断；`assumed`：仅用于演示的展示假设。每条关键行为记录分类与来源，冲突单列，不能以多数来源表决。
- 运行环境版本无法映射到源码时，两份基线分别记录，不能拼成“同版本证据”。未提交源码另存文件摘要和必要差异，HEAD 不能代表工作区全部内容。
- 模式：`source-and-runtime`、`source-derived`、`runtime-only`、`image-only`。后两种不推断隐藏业务；`source-derived` 不宣称与线上视觉一致。

## 范围与表现

页面状态按发现的关键路径和代表性组合确定，不强求枚举所有组合。未观察到的空、加载、失败、权限状态记录为缺口；有源码证据可先以推断状态实现。额外场景放在独立演示控制区，标记为演示，不伪装成原产品入口。

现状还原采用目标工程的既有视觉体系，遵循 [UI 规范](ui-standard.md) 的既有体系优先原则；与规则冲突的行为记录差异并按治理约定处理，不静默豁免，也不顺手改造现状。没有依据的部分保持待核实；UI 优化作为后续调整追踪。

## 隔离与资源

原型的 HTML/CSS/JS、本地数据和必要库均在原型根内可解析。不能导入服务仓库绝对路径或依赖作者电脑的 node_modules。记录提取资源的来源、摘要及第三方库版本/许可证。不得把整个业务服务复制为原型。

所有交互在本地模拟；真实提交、导入、删除等操作只表达结果，不调用真实业务 API。原始请求记录可能包含凭据和业务数据，采集前限定范围，归档前脱敏；无法脱敏的证据留在被忽略位置，只登记缺口，不提交 Cookie、Token 或真实凭据。原型演示使用合成或已授权脱敏数据。

## 验证与回流

分别记录结构/字段、交互、资源与网络独立性、视觉一致性四类结果：`passed`、`failed`、`not_verified`、`not_applicable`。后者要有理由。原型自己的截图是产物证据，不能作为原页面视觉基线。

视觉对比固定浏览器、视口、字体、缩放、时间和数据；比较同一状态。先设置关注区域和允许差异，阈值按试点确定，不能为变绿提高阈值或遮挡核心业务内容。没有原页面截图时视觉项必须 `not_verified`。

节点回流以 [workflow 的条件回流表](../workflow/prototype-reconstruction-workflow.md#条件回流)为准。06 同时检查实现与输入依据，不能把来源冲突或业务取舍当成实现错误。06可按需提前评审，07必须执行下述open-code-review收尾审核；提前评审不能替代收尾审核，代码审查也不能替代浏览器行为、视觉或动态网络检查。

检查性质必须与主张一致：日期筛选应保持重叠区间同井同日期数值一致；缺失输入与真实无数据分别验证；从失败恢复后核对关联字段和控件状态。仅有 CSP、资源引用或源码检查时只记录静态隔离证据，未实际监听的网络检查保持 not_verified，不能声称实际请求为零。

## 必需收尾审核

完整流程在07准备好本轮原型和交付资料后调用open-code-review，再决定最终状态；已构建的partial候选同样需要审核可交付部分。仅请求01–06中单一阶段时不自动扩大范围，单独请求07则包含本节。没有完成任何可审原型变更时也要核实范围，不能直接跳过并声称通过。

1. 固定本轮开始时的Git基线与工作区摘要，以及本轮累计原型变更清单。审查所有新增、修改、删除和纳入范围的未跟踪文件的最终状态；dirty起点用开始时的文件清单、摘要与必要局部差异核对，不只看最新提交、暂存区或最后一次修复。不要通过stage/reset/stash改变用户状态来适配工具。规格、验收和交付说明作为上下文；不把整个Harness无关变更混入原型审查。
2. 读取并使用官方 [open-code-review技能](https://github.com/alibaba/open-code-review/blob/main/skills/open-code-review/SKILL.md)；可采用其 [委托模式](https://github.com/alibaba/open-code-review/blob/main/skills/open-code-review-delegate/SKILL.md)，须实际运行OCR的范围/规则命令再由代理逐文件审核。记录工具、版本、模式、命令、原始结果与退出状态，不能将普通人工阅读标成已执行OCR。常规CLI模式使用 `--audience agent` 并把完整输出保存到文件；委托模式保存preview/rule输出、逐文件覆盖及结构化结论。
3. 将OCR范围与累计变更清单逐项对账。第三方压缩库、二进制素材等排除项写出理由及替代核验；被工具跳过的自写源码、截断内容、失败文件不能算已审。无有效报告、退出失败、覆盖不全或零reviewable文件都不能标passed；只有起点记录与范围证据证明本轮确无适用原型变更时，才可记not_applicable并说明原因。工具过滤导致的零文件不是无变更证明。
4. 将问题核实、去重并关联原issues/causeKey，保留误报排除依据。未解决的critical/high/medium原型缺陷阻止收尾审核passed；low作为有理由的建议保留。来源继承行为按既有取舍处理，不凭严重度自动改产品含义；尚待决定的阻断问题保持partial。
5. 按根因回流到必要节点；实现修复经05 → 06行为和关联回归后再次执行07收尾审核。每次复审仍对齐完整累计范围；未变文件只能凭已有审核记录与当前摘要相符复用覆盖，不能漏掉早轮产物。OCR发现的根因只有相应行为复测和审核复核均关闭后才归零，不能因06局部通过便清零后在07反复重开。
6. finalReview绑定累计范围清单摘要、来源baselineId、规格/验收摘要及逐文件最终摘要。被审内容、清单、来源、规格或验收条件变化均使当前passed失效，保留旧报告并重新复核。审核报告和纯状态回执属于输出，不加入自己的审核输入；单纯归档结果不触发自审循环，实质更改交付说明或业务约束仍须重新判断。
7. 工具缺失、配置/连接失败或预算耗尽时记录not_verified、具体原因和恢复条件，整体partial；按工具技能处理安装或配置，不索取或归档明文凭据，不无界重试。无法完成审核不阻止保存现场和交付partial报告，但不得将必需审核静默改为可选。

finalReview状态为pending / passed / changes_requested / not_verified / not_applicable。passed须有有效报告、完整范围对账及无未解决阻断问题；not_applicable仅适用上面证明的无适用变更情形。结论及历史尝试记录在finalReview和iterations中，iterations.node仍为'07'，action注明final-review或handoff。当前记录必须包含finalReview；尚未完成审核时保持pending。

## 循环记录与有效性

使用当前周期 reconstruction 记录，旁路模板 recordVersion 为 2；不修改 Manifest、Execution、Gate Schema。source、scope、states 继续持有来源、范围和状态定义，workItems 通过 stateIds 引用，不复制一套业务事实。

- loop：记录 runId、请求模式、当前节点/工作项、baselineId、输入摘要和停止上限，同时记录全局动作的执行次数与连续无进展次数。来源索引摘要必须覆盖源码 dirty 文件及运行环境的实际证据，未知部署版本保持未知；不得只用分支名或 HEAD 代表全部输入。
- workItems：稳定 ID、stateIds、依赖、涉及文件、当前节点、输入摘要、分项 checks 和遗留问题。状态为 pending / running / verified / partial / blocked；只有当前版本全部适用必需检查通过才标 verified。
- dependsOn：引用前置工作项及真正必需的检查，例如结构和交互。只有这些检查在当前摘要下通过才满足依赖；前置项单纯缺少不相关视觉证据不必阻止其他独立构建，禁止绕过已声明的失败依赖。
- iterations：每次节点执行追加一条，保存序号、实际时间、workItemId、node、输入输出摘要、result、changedArtifacts、affectedWorkItems、evidence、nextAction。node/targetNode 使用字符串 01–07；01/02/07 和全局回归的 workItemId 可为 null。result 为 done / partial / blocked，与检查 passed / failed 等枚举分开。
- nextAction：targetNode、workItemId、reason。暂停、最终退出或单阶段请求结束时 targetNode 为 null，并在 reason 记录建议去向或恢复条件；不把建议当成下一节点已执行。
- issues：每个问题保留 ID、稳定 causeKey、分类、来源归属、影响工作项、证据、状态和连续失败次数。同因问题合并，复发重新打开原问题；历史记录不删除。

01 建立来源基线 ID。每次规格或原型变动时更新相应文件摘要，检查结果必须附 evidence 和 checkedAgainst，绑定 baselineId、相关规格摘要及被检查的原型/资源文件摘要。报告文字“已通过”或节点 done 不能替代这些证据。states.verified 只表示其约定行为已有有效验证，不自动提升整个工作项或整体完成状态。

恢复时先核对最近一次已完成输出是否仍与工作区一致；中途被打断的写入只检查实际落盘内容，不重复叠加补丁。输入变更或摘要缺失时，从最早失效节点复核，不能跳过依据不足的阶段。既有节点不需要重跑时，iterations 明确引用复用的记录和摘要。

来源变化使受影响状态、规格及其后续验证失效；规格变化使依赖该规格的实现/验证待复核；原型共享样式、组件、Mock 或库变化使所有引用它的工作项和全局关联回归失效。依据依赖与文件引用计算影响；无法证明不受影响时扩大到同页或同共享资源的所有消费者。保留旧验证条目，在当前检查上标 not_verified 并注明失效原因，不能覆盖或挪用旧 passed。

全局 baselineId 改变时，未受影响项也必须先复核适用性。只有追加 evidenceReuse 记录，逐项给出 fromBaselineId、toBaselineId、workItemId、checkNames、来源差异证据及未变的规格/产物摘要，才可继续采用原检查；旧 checkedAgainst 保留原值，不改写成新基线。来源差异证据无法证明该项不受影响时按失效处理。汇总只接受直接匹配当前输入的检查，或存在上述有效适用性复核的历史检查，并标明“复用历史检查，非本轮重测”；新基线的全局关联回归仍需执行。首次运行没有旧检查时 evidenceReuse 为空。

iterations 追加过程证据，当前 workItems/checks 与顶层 validation 只做最新状态汇总。顶层 validation 必须覆盖 scope 内全部工作项和全局关联回归，不能仅汇总最后成功的一项。单项处于 partial 或 blocked 时仍计入覆盖分母。

## 问题归属与停止

问题按 implementation / specification / evidence / source / decision 分类，并记录 prototype / inherited / unknown 来源归属。只有证据支持的原型实现问题进入05修复；误报须保存排除依据，源工程继承行为保留现状并登记取舍，不能自动美化原产品。任何验收条件或允许差异的调整须有明确的新依据/授权、追加改动说明及必要局部差异并使相关验证失效，修复节点不得自行降低标准或重新截取基线来通过。

- 对同一 causeKey 连续两次修正后的复测仍失败，停止受影响工作项；仅发现问题或采集失败不算“已修正”。consecutiveFixFailures 只在有修复变更且复测后更新；OCR根因须满足收尾审核复核后才可关闭并归零。
- 连续两次节点执行没有新增有效证据、规格澄清或实现变更，停止该项空转；出现有效进展后 consecutiveNoProgress 归零。仅更新时间、换问题编号、重复同一截图不构成进展；从有效缓存推进到下游节点不算空转。
- 01 默认固定每个工作项最多 20 次节点执行，含回流和失败尝试；复用已完成节点不计执行。达到上限后禁止下一次执行，保留实际计数与原因。用户设置的更严格预算优先；恢复、更换记录或拆分同一失败项不得清零或自动放宽上限。确需调整时保留用户授权与原记录。
- workItemId 为 null 的来源核对、盘点、全局回归及07收尾OCR审核，在 loop.globalNodeExecutions 与 globalConsecutiveNoProgress 单独累计；默认最多20次全局节点执行，达到上限后禁止下一次执行，连续两次无进展即停止全局重试，有效进展使该无进展计数归零。一次完整OCR审核尝试（含必要preview/rule调用）计一次，失败尝试也计入。被全局问题影响的项标partial/blocked，其他有效独立项可继续。只有07保存现场和封包写报告免于重试上限，OCR调用与复核不豁免；达到上限后审核未完成则如实交付partial。
- 依赖未满足时不执行依赖项；必要证据不可获得、工具不可用、需业务决定或来源存在未解冲突时标 partial/blocked，记录恢复条件，继续其他独立项。已知不可获取的证据不必先重试两次。

队列无可运行项后，06 检查覆盖分母、当前证据有效性以及跨状态转换、共享资源和关键主路径的关联回归。回归失败按同一问题规则回流，达到停止条件则保留缺口进入07；不得为交付无限重开停止项。

07 仅在所有适用必需检查与关联回归通过、收尾OCR状态为有效passed或有证据的not_applicable、无未解决阻断时记录completed；其余记录partial。loop.finished表示本次执行已结束，可对应partial，不代表通过。未完成的单阶段请求按实际内容交付，不把未执行的其余节点设done。人工UI确认仍走既有Gate。
