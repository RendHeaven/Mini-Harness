# 前端 UI 工程计划

## Objective

从 PRD、项目原型与真实前端工程形成逐页计划、复用决策和可验收 TASK。

## Inputs

- 产物相对[工作流](../../workflow/frontend-workflow.md#阶段执行)指定的阶段根。
- 文档遵循[时间规范](../../rules/document-timestamps.md)。
- 必需：当前 PRD、项目根原型仓库及已消费变更引用、项目服务目录与拓扑、目标服务目录、目标前端 AGENTS、源码、`rules/ui-standard.md` 和 `rules/frontend-engineering.md`。
- 可选：Dev Guide、UI Handoff；作为补充，不代替 PRD 和原型。
- 工程目标不存在或产品语义冲突时记录告警和真实 `blocked` 状态，在可规划范围内继续，不得补造工程事实或产品/UI 结论。

## Workflow

1. 核对 REQ、原型来源、精确服务 ID、服务角色、版本分支和来源哈希。服务角色以真实工程和拓扑判定为 `host`、`micro-frontend` 或 `standalone`，不得只写“主应用”“子应用”。
2. 一个目标服务生成一套独立 UI Plan：`1-ui-plan/`。
3. 搜索当前服务的页面、路由、组件库、业务组件、Token、Hook、工具函数、状态、权限、请求/服务能力和测试设施；读取候选实现及调用方，记录真实路径、导出入口与适用边界。其他服务只作为协作方记录其服务 ID、真实职责和契约。
4. 当需求同时影响主应用与微前端时，明确每一层导航归属、路由发起方、激活态同步、传入数据、事件名、降级行为和回归责任；双方总览必须记录同一份跨服务契约。
5. 按真实页面判断本页是否适用表格、图表、格式化与权限入口；对照栏填写 `applied|not-applicable|issue`，约束分别见 `rules/ui-standard.md` 与 `rules/frontend-engineering.md` 对应节，不沿用上游错误的 `not-applicable`。
6. 按下述四项设计和权限要求填写页面方案。
7. 按下述页面边界拆分 PLAN，并登记总览映射。
8. 逐页填写组件与逻辑复用方案，按下述决策要求核对证据。
9. 按下述 TASK 边界分解页面交付，并关联共享依赖、回归和验收。
10. 使用 `template/develop/frontend/ui-plan-template.md` 生成总览，并按 `template/develop/frontend/ui-plan-module-template.md` 生成每个 PLAN 文件；清空待确认项或如实标记阻塞。

## Decision rules

- 按页面拆分 PLAN，一个页面对应一个 PLAN 文件；在总览列出页面、路由或承载入口与 PLAN 的映射。不得按技术层、公共组件或样式/交互/路由/权限维度分别拆 PLAN，也不得把多个独立页面合为一个大模块 PLAN。
- 每页填写组件与逻辑复用方案：分别评估 UI 组件与表单校验、查询分页、状态处理、权限判断、路由参数处理等适用逻辑，记录现有实现、适配差异、直接复用/扩展已有/抽取共享/页面内新增的决策及理由、改动边界、调用方影响和验证方式。未找到合适实现时写明检索范围与不采用候选的原因；来源不可读时如实记录缺口，不得推定实现不存在。
- 在每个页面 PLAN 内按可分配、可单独完成和验证的最小结果拆分 TASK，记录 TASK 依赖、风险、回归半径和测试，并关联复用方案。TASK 不单独生成计划文件；跨页面共享改动指定一个页面 PLAN 中的 TASK 负责，其余消费页面引用依赖并规划各自回归。
- 不改变 PRD 或 UI Handoff；语义变化记录为职责问题，先询问用户按哪个角色处理。
- 服务 ID 是研发目录、PLAN/TASK、验收和发布的边界，不混入其他服务源码任务。未明确影响源码的服务只能作为外部依赖，不得补造实现 TASK。
- 页面边界以 PRD 与真实工程的独立访问和验收单元为准：列表页与独立详情页分别建 PLAN；附属弹窗、抽屉和页内 Tab 纳入所属页面，具备独立页面职责时单独规划。无独立 URL 的页面写明承载入口与导航责任，不得补造路由。
- 每页包含四项设计：样式（布局、组件、视觉来源、尺寸适配及各状态）、交互（触发动作、校验、状态流转与反馈）、路由（入口、路径/参数、跳转/返回、刷新与深链）和权限。复用现状写明来源及本次变化；不适用项说明依据，待确认项记录缺口。共享组件归属页面内部 TASK 或跨页面依赖。
- 组件与逻辑复用先核对真实实现，再决定新增或抽取；不得只写“复用公共组件”或以复制代码代替复用评估。外观或代码相似不足以证明业务语义一致，不为假设中的未来需求建立通用抽象；仅本页使用的能力可保留在页面内部。
- 扩展或抽取共享能力时，明确组件输入/事件或函数输入输出、状态归属、兼容已有调用方的方式和回归范围；同一 Hook 被多页调用不等于需要共享状态。跨服务复用遵循已有公共包或契约边界，不直接依赖另一服务内部源码。
- ui-exec 核对实际代码后发现复用假设不成立时，记录证据与影响并回流 ui-plan，再调整关联 TASK 和依赖。
- 微前端导航的同一层级只能有一个责任服务。主应用与子应用分别规划各自持有的导航层与内容层；跨服务同步只能通过明确契约，不能以重复渲染替代。
- 不因接口未就绪省略 UI 状态，可使用与已知语义一致的临时 Mock。
- 工程边界对照栏不得留空；没有对应能力时写 `not-applicable` 并说明。
- 权限总览记录来源与跨服务责任，页面设计关联 REQ、页面/路由/操作、角色或条件、真实权限标识及判断入口、数据范围、无权限表现和 TASK 验收；不得只写“按现有权限处理”。不涉及权限时写 `not-applicable` 及依据。权限语义以已确认 PRD 为准，权限标识、获取与判断方式须引用真实工程或已确认契约；新增权限点记录注册/配置责任与依赖。不得自行编造角色、权限码或授权范围；缺失或冲突时记录缺口、责任方及回流位置，受影响 PLAN 保持真实 `draft|blocked`，继续其他可规划工作。
- 权限规划分别覆盖适用的菜单/页面访问、按钮/行操作和数据/字段范围；入口可见性遵循 `rules/ui-standard.md`，并明确直接访问路由、权限加载中、权限获取失败及登录失效/权限不足的处理。前端控制不能替代服务端鉴权；服务端责任和待对接契约作为依赖交给 API Plan。
- 权限验收关联对应 TASK，至少覆盖有权限、无权限和直接访问受限路由；涉及数据范围、权限变化或跨服务权限传递时补充相应场景。不适用的场景说明原因，不能以隐藏入口作为全部权限验收。

## Output contract

每个目标服务输出 `1-ui-plan/plan-overview.md` 与 `1-ui-plan/plan-01.md` 至 `plan-编号.md`，分别使用总览模板和单页模板。不得生成聚合 `1-ui-plan/plan.md`、`1-ui-plan/tasks/` 或 `task-编号.md` 等独立 TASK 计划文件。

按页面拆分且上述设计、复用、TASK 和验收均明确后标记 ready，否则保留真实 `draft|blocked` 并告警，均允许后续阶段继续检查。
