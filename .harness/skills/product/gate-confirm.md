# 产品 Gate 确认

## Objective

通过产品反问收束当前交付的决策，再取得真实产品 Gate 确认，保留实际来源和操作证据。

## Inputs

当前 PRD、修订链、原型、Discovery、Mock 记录，以及可访问的已有反问对话和决策依据。进入阶段不要求已经取得负责人确认；最终记录 Gate 时必须取得针对当前交付的真实确认。

## Trigger

- 已选择产品角色的完整产品流程推进到本阶段，或用户明确要求“进入产品确认”“确认这个需求”等时，检查当前交付并自动调用[产品反问](prd-review.md)，直接开始第一轮，不额外询问是否启动。
- 只要求生成、修改或导出 PRD 时，在指定任务结束后停止，不因首次交付、保存或修订完成自动启动反问。用户单独要求反问仍可调用该技能，但不因此进入 Gate 确认。
- 触发依据是当前任务推进到本阶段，不是后台文件监听。进入阶段、说“准备确认”或回答某道反问，都不等于最终交付确认。

## Workflow

1. 使用 tools/role_gates.py --project-root <根> --cycle <周期> 查看自身问题，识别当前交付和已有确认所覆盖的内容。仅重复查看且内容未变时保留已有有效确认；确需重新开展确认工作时进入 in_progress，保留历史记录。
2. 检查交付完整性并处理可直接查证的缺口；业务待确认项交给反问，缺少材料时说明未决前提，不伪造已完成检查。
3. 按下述复用规则调用[产品反问](prd-review.md)：分轮提出全部前置条件明确的问题，每题给推荐答案，等待真实回答。没有待决问题且查证完整时，简述共同理解，直接准备最终确认，不为完成步骤凑问题。
4. 回答不改变当前交付时，将共同理解与当前 PRD、原型和修订记录一起展示，进入 pending_confirmation；一次明确询问“以上理解是否一致，并确认当前产品交付？”即可覆盖两项确认，无需连续询问两次。
5. 回答改变业务规则或交付内容时，先收束并确认共同理解，再在已有授权范围内更新 Discovery、PRD 修订及受影响原型。修订后核对回答是否准确落地，仅对新增或受影响分支继续反问，不从头重问。内容稳定且自身检查完成后进入 pending_confirmation，展示修订结果，请负责人确认最终交付；修订前的答复不能确认修订后的内容。
6. 只有实际负责人明确确认当前最终交付后，才用 --role product --status confirmed --actor <确认人> --reason <依据> 记录。仅认可共同理解、部分回答或沉默均不足以记录 confirmed；若已在同一次答复明确确认两项且交付未再变化，不重复索要确认。
7. 记录确认人、时间、范围、来源路径及已覆盖的 CHG/原型变更引用；引用真实确认依据，不重置其他角色。记录前如来源再次变化，先复核受影响内容并取得对最新交付的确认。

## Reuse

- 复用必须能把已有结论关联到当前 PRD、原型、Discovery 和相关事实；可使用可访问对话、DEC、逐次变更记录及实际 Git 提交核对，不新增强制反问报告、PQ 表或状态文件。
- 内容与前提均未变时复用已有回答，只处理未决分支。业务变化只重开受影响决策及其下游分支；已按明确回答落地的修订先核对一致性，不把这次修订本身当作全量重问理由。
- 跨会话缺少先前问答或无法确认其覆盖范围时，先展示从现有产物还原的理解让负责人核对，再补问不明确的部分；不能凭“反问过”或既有 Gate 记录推定本技能已经执行。

## Decision rules

确认遵循 [Gate 协议](../../rules/review-gates.md)（含确认者 Git 身份）；文档遵循[时间规范](../../rules/document-timestamps.md)。

## Output contract

反问阶段输出对话中的问题、推荐答案与收束结论；需要修订时使用既有产品产物和修订记录。最终明确确认后交付 product Gate 独立确认记录、已覆盖变更范围和证据路径，不强制新增 PRD Review。
