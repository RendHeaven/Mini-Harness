本手册面向测试工程师 / QA，用于影响分析、测试设计、用例同步、执行与缺陷回流。描述的是当前工作区能力，实际使用以项目锁定的 Core 原文为准。示例中的版本、路径和服务 ID 均需替换为真实值。

**你的职责：**验证业务和变更影响，区分资料缺口、用例同步及实际执行结果。入口：[TestHub Workflow](../.harness/workflow/testhub-workflow.md)。

## 开始前准备

确认当前需求版本、实际研发证据、PRD、可用 UI/研发产物、结构化接口文档及前后端 revision；同步前核对项目 `.harness/projectContext/testhub.yaml`。TestHub 是需自建或适配的外部测试服务，`baseUrl` 未替换为真实地址前只能生成文档，不能同步或执行。缺少资料时可以生成有事实支撑的用例，但必须记录未参考的来源和覆盖缺口。

## 按顺序操作

1. 分析代码差异和调用关系，覆盖直接改动、间接影响及未改但需要回归的功能，生成 `change-impact-analysis.md`。
2. 运用等价类、边界值、场景、状态转换等方法，生成 `test-design.md` 与 `coverage-matrix.md`；没有依据的上限、指标口径或 SLO 记为缺口。
3. 生成完整 `cases.md` 与 `generation-report.md`，将用例关联到需求、影响项及具名缺口。
4. 先做本地 Markdown/JSON/变量/Fixture/Mock 校验，再将完整当前用例集同步到 TestHub，保留 `sync-metadata.json` 与 `sync-report.md`。
5. 用户明确要求执行时，使用本次导入返回的用例集及 revision 发起 Run，记录 `run_id`、启动状态、终态和明细；按需通过 `retry-failed` 重试失败用例。

以上文件默认位于需求周期的 `develop/testhub/`。历史用例可作为回归候选，历史通过结论不能替代本期执行。

## 可复制指令

```text
我是 QA，请为 v1.2 做测试设计与完整回归用例生成。
结合前后端真实 revision、代码差异与调用链，覆盖直接、间接及未改回归功能，
输出影响分析、测试设计、覆盖矩阵、cases.md 和来源账本。
本次只生成和本地校验，不上传、不运行。
```

```text
请将已校验的 v1.2 完整 cases.md 同步到项目配置的 TestHub，
保留稳定 ID、幂等键及脱敏回执，返回同步数量与 blocked 原因。
```

```text
请执行本次同步回执对应的用例集 revision，目标测试环境为<环境>。
记录 run_id、实际启动状态、终态及失败明细；环境阻塞单独说明。
```

## 结果怎么读

| 结果 | 含义 |
| --- | --- |
| `generated-with-gaps` | 已生成，但上下文或覆盖有缺口 |
| `invalid-for-sync` | 本地结构/安全等校验不满足，不提交同步 |
| `skipped-no-cases` | 没有正式用例，不上传空文档 |
| 导入成功 | 仅说明文档同步成功，未必执行过测试 |
| 接受 Run 请求 | 还需核对 `execution_started` 及后续终态 |
| 执行失败或环境阻塞 | 保留失败/阻塞原因，不能记为测试通过 |

TestHub Harness 生命周期接口按当前集成协议无需账号密码或 Token，但只适用于 Harness 导入项目；这不代表被测系统或管理接口无需鉴权。不要上传被测系统密码、Cookie 或登录态。

缺陷按 [Bugfix Workflow](../.harness/workflow/bugfix-workflow.md) 记录复现步骤、预期/实际行为、版本和服务；确认根因后交给责任开发，修复后核对实际 revision 与回归证据。
