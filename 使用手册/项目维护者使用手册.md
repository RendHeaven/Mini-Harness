本手册面向项目负责人 / 项目 Harness 维护者，用于初始化项目、管理 Core pin、维护服务映射与交接。描述的是当前工作区能力，实际使用以项目锁定的 Core 原文为准。示例中的版本、路径和服务 ID 均需替换为真实值。

**你的职责：**让项目成员访问一致的规则和真实工程上下文，维护交接与采用范围。入口：[项目模板说明](../project-harness-template/README.md)。

## 新项目接入

1. 准备团队确认的 Atlas Git checkout、项目 Harness 仓库和服务仓库，明确各自位置。
2. 从 `project-harness-template/` 采用 `AGENTS.md`、`.gitignore`、`.codex/`、`.harness/`。已有项目逐项合并，保留定制和本地配置。
3. 填写 `.harness/harness.yaml` 的项目 ID/名称与 Core pin。`localPath` 相对项目 Harness 根；version、revision、contentHash 必须对应同一真实 Core 提交。
4. 填写 `project-context.md` 与 `services.yaml`，明确真实 service ID、仓库、职责、契约、数据归属和依赖。
5. 按需配置 TestHub、Jenkins 映射及本地数据库工具；不将模板占位值当成已接入结果。
6. 配置运行端加载项目入口，执行项目校验，并从各角色的开场指令验证能否定位正确 Core 与服务。

## 项目 hook 与 Atlas hook 的关系

项目 `.codex/hooks.json` 注册事件，调用项目 `.harness/hooks/usage_hook.py`；该入口再从 `core.localPath` 加载 Atlas 通用采集器。项目负责接入和环境定位，Core 负责通用采集实现。它们是一条调用链，不维护两套采集逻辑。

hook 是否生效取决于运行端是否加载配置；它不替代 workflow、Gate、版本 pin 校验，也不自动触发 Jenkins。采集范围、目录与关闭上传方式见 [Collector 说明](../.harness/hooks/README.md) 和项目模板说明。不要把“文件已复制”报告为“采集已验证”。

## 日常协调

```text
请检查项目 v1.2 当前交付状态，按产品、UI、前端、后端、QA 列出：
已有产物、来源是否有效、真实验证结果、未确认事项、责任人与下一步。
Gate 告警和实际阻塞分开说明，不把 phase completed 解释为已上线。
```

升级 Core 前明确目标提交、变更影响、项目定制和采用范围；升级后运行严格项目校验。不要只修改版本号消除漂移，不自动升级其他项目。需求修订时通知所有受影响角色刷新派生产物。

Gate Schema 2、Execution Schema 7 与 PRD 修订 Schema 2 保存实际确认事件、来源及变更记录。无法核实的确认范围记为未知，不补造为新确认；独有截图、测试报告等按实际验证需要保存。
