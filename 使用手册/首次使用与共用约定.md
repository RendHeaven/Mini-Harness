## Atlas、项目 Harness 与服务仓库

| 位置 | 保存什么 | 日常做什么 |
| --- | --- | --- |
| Atlas-Harness | 团队通用 workflow、skill、规则、模板、Schema 和校验器 | 读取当前项目锁定的规则；通用能力变更由 Core 维护者处理 |
| 项目 Harness | 产品事实、需求周期、服务索引、计划与交付证据 | 创建需求、规划、评审、记录测试与构建结果 |
| 前后端服务仓库 | 源码、构建配置、契约、数据与部署事实 | 实现、测试、提交代码，维护 Jenkinsfile 与部署清单 |
| 客户端本机 | 本地连接配置、运行环境和凭据 | 提供数据库配置、MCP 连接与必要工具 |

推荐工作区同时能访问项目 Harness、其锁定的 Atlas checkout，以及本次受影响的服务仓库。不要把实际项目 PRD 或服务源码放进 Atlas Core。

本手册使用标准目录 `.harness/`。下文的路径是默认模板布局，自定义项目以 `.harness/harness.yaml` 为准。

## 第一次进入项目

1. 打开项目 Harness，读取 `AGENTS.md` 与 `.harness/harness.yaml`。
2. 确认 `core.localPath` 指向可读的 Atlas checkout；核对 version、Git revision 与 contentHash。发现漂移时交给项目维护者处理。
3. 确认需求版本，例如 `v1.2`，以及目标服务在 `.harness/projectContext/services.yaml` 中的真实 ID、仓库位置和职责。
4. 产品、UI、研发、测试与 Bugfix 按角色任务读取对应 workflow，再进入具体 skill；Jenkins 属于独立按需能力，直接从能力入口或项目 AGENTS 进入 skill。自然语言即可发起，不要求记住内部工具名。
5. 任务结束时查看真实产物、验证结果、未完成事项与下一位责任人，而不仅是聊天中的“已完成”。

可复制的开场指令（尖括号内容先替换）：

```text
我负责<角色>。项目 Harness 位于<路径>，需求版本是<版本>，目标服务是<服务 ID>。
请先读取项目 AGENTS.md、harness.yaml 和项目锁定的 Atlas Core，
确认当前阶段和已有产物，再按对应 workflow 或独立 skill 执行<本次任务>。
已有输入：<文档路径/需求说明/代码 revision>。
完成后返回产物位置、实际验证结果、缺口和下一步交接对象。
```

这些示例是发给助手的自然语言任务，不是 shell 命令或已安装的斜杠命令。规划、实现、上传、执行构建应说明本次范围；已有明确授权持续有效，关键目标缺失时补齐即可。

## 如何理解阶段完成和 Gate

项目根 Gate.yaml 维护 product、ui、frontend、backend 四角色独立状态，彼此没有通过依赖。TestHub 保留测试能力，不设置第五 Gate。
每个 confirmed 必须绑定实际负责人、时间、证据和 PRD/原型版本。机器检查不能代替确认。输入变化由各角色独立复核，不自动级联重置。
Manifest phase 仅记录实际进展，不从 Gate 推导。角色确认不等于测试完成或上线。

原型只在项目根原型仓库持续维护，不按周期复制。前后端共同读取 PRD 和原型。
